# C07.8–10. Протокол v1

До сравнения: одинаковые Q4_0 и входные ID, CPU FP32 K/V, четыре потока; сравнить все последние 32768 логитов на каждом шаге и требовать одинаковых greedy ID. Порог max abs 0,15 для Q4_0 с разными размерами матричных операций GGML. При превышении опубликовать результат. Контроль без кэша сохраняется.

Локальный HTTP API v1: GET /ready и POST /generate с JSON {"text":"Привет","max_new_tokens":4}. Ответ содержит text и ids. Ошибки: 400 при неверном вводе, 422 при переполнении окна вместе с BOS и бюджетом ответа, 429 при заполнении очереди. Сервер привязан к loopback. SIGINT завершает приём запросов и позволяет завершить уже принятые. Несовместимость GGUF и C02 останавливает запуск до готовности.

## C07.7 и протокол C07.8

PR #19 слит в main (da58aeb); исходное измерение на M1 — [0,432 токена/с](cli-runbook.md#приёмка-c077-на-mac). Для повторения парного теста запустить из корня после сборки CLI и CPU runner по инструкции C07.7:

```sh
python scripts/check_c07_kv.py "$PWD/rust/target/release/burda-generate" "$GGUF" "$work/cpu/bin/burda-ggml" /tmp/burda-kv-results
```

Скрипту нужны numpy и psutil. Каталог результата должен быть новым. Полный префикс (`--kv off`) и кэш (`--kv on`) используют одинаковый Q4_0, вход, число потоков и backend. При включённом кэше после prefill передаётся один новый ID с позицией на единицу больше предыдущей. На коротком префиксе сверены четыре полных вектора последней позиции. Максимальные ошибки: 0, 0,0752333, 0,0842509 и 0,0806652; в обоих режимах greedy ID равны 13248, 13248, 7146, 11674. Допуск 0,15 опубликован в 9c7c881. Отличие путей Q4 GEMM и однотокенного GEMV измеряется вместе с эффектом кэша.

При длине 4096 CLI завершился без следующего шага; при 4097 вернул ошибку. Для проверки EOS в копии синтетического GGUF строки 2 и 13248 матрицы token_embd.weight обменяны местами. Вход из BOS и шести повторений « a» дал EOS на первом шаге; ноль выданных ID при лимите 4. Запросы однопроцессного CLI имеют отдельные контексты; выход процесса освобождает их и при ошибке.

## C07.9. Группа из двух запросов

Постоянный процесс загружает одну модель и обслуживает до двух запросов за тик, параллельно в двух контекстах GGML по 4096 позиций. У каждого свой KV, позиции, EOS и лимит. Вариант с одной объединённой матрицей токенов дал расхождение последнего greedy ID при отмене соседа на тестовых Q4-весах; для v1 выбраны изолированные контексты с общими весами. K/V двух полных окон занимает 640 МиБ. При окончании, отмене или ошибке слот очищается. Протокол допускает очередь из двух ожидающих запросов; большее накопление не увеличивает вычислительный параллелизм.

На M1, для запросов 7→4 и 4→8, задержки одиночных прогонов после загрузки — 0,158 и 0,207 с. Вместе — 0,213 и 0,266 с, 45,06 токена/с суммарно, наблюдаемый RSS backend 1 234 845 696 байт. Все 12 ID совпали с одиночными прогонами. Проверены отмена после первого ID, ошибочный запрос в освободившийся слот, завершение короткого запроса и повторное использование того же слота. Команда: python scripts/check_c07_slots.py "$work/cpu/bin/burda-ggml" "$GGUF".

## Чистая сборка и приёмка C07.10

Тестовая платформа — Apple M1, 8 ГиБ, macOS 26.7.1, Rust 1.100.0, CMake 3.31.6. Зависимости Rust закреплены Cargo.lock (Axum 0.8, Tokio 1, tokenizers 0.21.4). GGML берётся из llama.cpp 74d4f5b041ad837153b0e90fc864b8290e01d8d5. Синтетический Q4_0 занимает 546 977 056 байт; SHA-256 a4d49d2b9bfc9d2d4ec7715587acb72693125387310a765c333fd8682c3314fd. Для получения весов из C07.5 см. [конвертацию GGUF](weak-pc.md). Исходный хеш tokenizer.json — 04efc216e2a03fb974f1420b77c5d631f01d4c3edbaa4b628808b64d96f30413.

Из свежего клона ветки, с установленными Rust, CMake и C++17:

```sh
work=$(mktemp -d)
export CARGO_HOME="$work/cargo"
git clone --depth 1 --branch b5046 https://github.com/ggml-org/llama.cpp.git "$work/llama"
runtime/ggml/build.sh "$work/llama" "$work/cpu" cpu
cargo build --release --locked --manifest-path rust/Cargo.toml --bins
cargo test --release --locked --manifest-path rust/Cargo.toml
cli="$PWD/rust/target/release/burda-generate"
server="$PWD/rust/target/release/burda-api"
runner="$work/cpu/bin/burda-ggml"
"$cli" --gguf "$GGUF" --runner "$runner" --tokenizer artifacts/c02-v1 --text 'Привет, мир!' --max-new-tokens 4
"$server" "$runner" "$GGUF" artifacts/c02-v1 8080
```

```sh
curl --fail http://127.0.0.1:8080/ready
curl --fail -H 'Content-Type: application/json' -d '{"text":"Привет, мир!","max_new_tokens":4}' http://127.0.0.1:8080/generate
```

CLI и API используют один CPU runner GGML и общий Rust-код токенизации. Сервер проверяет идентификатор модели и загружает контексты до открытия порта. Ожидаемый результат запроса на тестовых весах — ID [19780,13362,13344,30839]. Оба активных слота используют до четырёх CPU-потоков каждый. Ещё два запроса могут ждать. Предел входа с BOS и заявленным бюджетом вывода — 4096, максимальный HTTP body — 256 КиБ. При HTTP 429 повторить запрос после освобождения слота. При 503 проверить stderr runner. Прерывание Ctrl-C закрывает listener и позволяет завершить принятые запросы. При отключении получателя планировщик отменяет слот на границе тика. Локальный API рассчитан на CPU GGUF; внешний сетевой доступ и аутентификация выходят за рамки v1.

Проверка на свободном локальном порту:

```sh
python scripts/check_c07_api.py "$server" "$cli" "$runner" "$GGUF"
```

Сценарий проверяет readiness, сравнивает вывод с CLI, проверяет 400, 422 и 429, отказ запуска при подмене связки tokenizer_id, затем завершает сервер сигналом SIGINT с активным запросом. Для воспроизведения нагрузочных измерений выше нужны Python 3.12, numpy 2.2.6 и psutil 7.1.0. Приведены отдельные прогоны на синтетических весах, без претензии на статистическую оценку быстродействия. Приёмка качества обученных весов относится к C06. Профиль Vulkan 1 ГиБ сохраняет полный префикс по умолчанию и остаётся отдельной аппаратной проверкой C07.6.
