# C04. Подготовка данных

Цель — подготовить воспроизводимые выборки русского и английского текста для обучения, настройки и итоговой оценки. Авторская литература пользователя запланирована как отдельный источник русского текста. Конкретные произведения и остальные источники согласуются в C04.1.

## Источники и преобразования

Для каждого источника зафиксировать происхождение, способ получения, неизменяемую версию, условия использования для обучения и распространения производных артефактов, язык и доступные метаданные. Источник включается после проверки этих условий. Правила качества, обработки персональных данных и удаления повторов утверждаются вместе со списком источников.

Порядок обработки — извлечение текста, присвоение стабильного идентификатора документа, фильтрация и канонизация для сравнения, группировка дубликатов, разбиение групп, токенизация, формирование окон и сборка шардов. Документы из одной группы получают одну выборку. Версии правил, алгоритм группировки, seed или стабильная хеш-функция и доли разбиения фиксируются в конфигурации. Баланс русского и английского публикуется по документам и токенам.

- **train** используется для обновления весов и при необходимости для обучения токенизатора.
- **validation** используется для настройки и выбора контрольной точки.
- **test** откладывается до итоговой оценки по C06. Дубликаты и фрагменты одного исходного документа не распределяются между выборками.

## Авторская литература

Для каждого произведения записать внутренний идентификатор, версию рукописи, условия доступа и согласованный объём использования для обучения и оценки. Группировать главы, отрывки и редакции по произведению до разбиения. Файлы и цитаты из неопубликованных произведений добавляются в репозиторий или публичные отчёты только по отдельному согласованию. В отчёте показывать долю литературного текста в русском корпусе и метрики по этому жанру отдельно. До получения материалов источник учитывается в плане, фактический объём не определён.

В манифесте сохранить ссылку на страницу и авторов через историю, применимую версию лицензии и описание преобразований. Для каждой статьи сопоставить текст снимка с постоянной ссылкой на редакцию (oldid), проверить нижний колонтитул, историю, обсуждение, пометки об импорте и цитировании. В журнале решений сохранить ключ статьи, SHA-256 извлечённого текста, oldid, ссылки на подтверждения, точную версию лицензии, обязательную атрибуцию, дату и результат проверки. Повторное рассмотрение требует нового подтверждения и записи решения. Для решения о публикации весов ведётся отдельное согласование. ### Фильтрация и контроль повторов

1. Принимать валидный UTF-8 с непустым текстом и идентификатором. Исключать NUL, символ замены U+FFFD, управляющие символы кроме табуляции и переводов строк. Из Википедии исключать перенаправления, страницы разрешения неоднозначностей, списки без связной прозы и статьи короче 50 слов. Слова для порогов — непрерывные последовательности букв Unicode. Если в статье меньше 60% букв ожидаемого письма (кириллица RU, латиница EN), отправлять на ручную проверку. Литературу проверять по языку и разметке автора, сохраняя короткие главы, диалоги, пробелы и абзацы.
2. Отмечать личные контакты, адреса проживания и приватные данные третьих лиц. Спорные документы откладывать до проверки. Вести счётчики причин по источнику и языку. Для обучения сохранять принятый исходный текст. Для поиска совпадений отдельно строить ключ сравнения: Unicode NFC, casefold, замена серий пробельных символов одним пробелом, удаление крайних пробелов.
3. Сравнивать документы глобально до разбиения. Точные дубли находить по SHA-256 ключа с проверкой равенства строк. Для близких копий сравнивать множества последовательностей из пяти слов. При наличии хотя бы 20 общих различных последовательностей связывать пару, если Жаккар ≥ 0,85 или доля общих последовательностей в меньшем документе ≥ 0,90. Второй критерий ловит отрывки. Зафиксированные связи по произведению, исходной статье и известным переводам действуют независимо от текстового сходства.
4. Внутри точных и близких полных копий оставлять один текст (приоритет предпочтительной редакции автора, затем минимального document_id), сохраняя ссылки на все источники и условия доступа. При совпадении отрывка с полной версией оставлять полную версию, если её использование разрешено. Уникальные главы сохранять. Если передано несколько редакций, использовать выбранную автором редакцию, остальные учитывать при поиске связей. При конфликте разрешений откладывать группу до уточнения.
5. Для защиты оценки сверить кандидатов с train Russian GSD и English EWT токенизатора C02: точное совпадение нормализованного предложения от 10 слов или близкий документ по правилам выше закрепляет связанную группу за train. Совпадения с dev пилота C02 исключать из test, поскольку они участвовали в выборе токенизатора (при попадании в test переносить группу в validation). Сами UD-наборы в реестр обучающего корпуса v1 не входят.

### Разбиение групп и проверка

До удаления копий построить граф связей и взять компоненты связности. Статьи связываются по исходному ключу, главы, редакции и отрывки — по `author:<work_id>`. Связь через копию в другом источнике объединяет компоненты транзитивно. Для группы выбрать лексикографически минимальный UTF-8 ключ источника/произведения. Взять первые 8 байт SHA-256 от UTF-8 строки `"c04-v1\n" + ключ` (LF), прочитать как беззнаковое big-endian число и взять остаток по модулю 10000. Интервалы 0–8999, 9000–9499 и 9500–9999 задают соответственно **train 90%, validation 5%, test 5%**. Приоритет имеет ограничение по C02 из пункта 5. Это целевые доли групп. Итоговые доли документов и токенов показывать отдельно по языкам, источникам и литературе. При малом числе произведений возможен пустой литературный срез. Отразить это в отчёте, сохранив произведения целыми.

Контрольный пример: две главы и ранняя редакция с ключом `author:book-A` связаны по произведению. Копия второй главы в `ruwiki:17` попадает в ту же компоненту. Минимальный ключ `author:book-A` даёт 8709, поэтому все четыре записи до удаления копий относятся к train. При сборке проверять для каждой компоненты ровно одну метку выборки, ноль общих work_id и хешей текста между парами выборок и воспроизводимость назначения при перестановке входов. Список групп, причины исключения и контрольные суммы входят в версию сборки.

## Предлагаемый интерфейс C04 → C05

| Объект | Обязательные данные |
| --- | --- |
| Запись | `document_id`, индекс окна, последовательность `input_ids` длиной от 2 до 4096 |
| Шард | Идентификатор выборки и шарда, число записей и токенов, контрольная сумма |
| Манифест | Версии источников, правил сборки и формата, `tokenizer_id`, `vocab_size`, параметры разбиения, перечень шардов и статистика по выборкам и языкам |
| Пакет C05 | `input_ids` и булева маска действительных позиций. Пакет формируется правым дополнением в загрузчике |

Документ получает BOS перед первым токеном и EOS после последнего по согласованным правилам C02. Для документа длиннее окна предлагается разбивка с перекрытием в один токен, чтобы каждый соседний переход встречался ровно один раз. Окна с менее чем двумя токенами отбрасываются. Независимые документы в одной строке не объединяются. C04 не сохраняет сдвинутые цели. C05 формирует их после пакетирования.

Контрольный пример для тестового окна длины 4 — последовательность `[BOS, 3, 4, 5, 6, EOS]` даёт окна `[BOS, 3, 4, 5]` и `[5, 6, EOS]`. Переход `5 → 6` сохраняется, а переход от EOS к дополнению исключается.

## Приёмка

- **C04.1.** Утвердить реестр источников, фильтры, единицу разбиения, обработку дубликатов и доли выборок. Проверить, что контрольные группы пересекающихся документов попадают в одну выборку.
- **C04.2.** Зафиксировать схему записей, физический формат и порядок чтения. Передать C05 контрольные окна, пакет с дополнением и ожидаемые цели.
- **C04.3.** Собрать выборки, проверить соответствие манифеста и шардов, валидность ID, длины и отсутствие перекрытия групп между выборками. Повторная сборка контрольного набора воспроизводит порядок записей и принадлежность к выборкам. Приложить команду, сводку отфильтрованных записей и распределение токенов.

### C04.2. Физический формат и контрольный пакет v1

Один UTF-8 JSONL-файл на выборку в контрольном наборе. Каждая строка — объект с обязательными полями `document_id` (строка), `window_index` (целое от нуля внутри документа), `input_ids` (массив целых от 0 до vocab_size−1). Читать строки последовательно, в порядке document_id и числового window_index. Для многошардовой поставки манифест перечисляет шарды в порядке чтения. Боковой реестр сопоставляет document_id с языком, происхождением и group_id. Проверять версию формата, идентификатор токенизатора, размер словаря и SHA-256 шарда до использования.

Окно в поставке модели — до 4096 ID. В контрольном наборе ширина 8, шаг 7, чтобы короткие тексты проверяли стык окон. Включать BOS/EOS один раз на документ. В C05 выровнять строки справа PAD=0 и передать модели вход полной ширины. Для позиции t целью служит следующий ID, последняя цель — служебное значение −100. В loss включать только позиции, у которых маска действительна и в t, и в t+1. Переданный в C05 [эталонный пакет](../fixtures/c04/expected/report.json) содержит input_ids, attention_mask, targets и loss_mask. Эти три производных поля вычисляются при пакетировании.

[Контрольные документы](../fixtures/c04/documents.jsonl) — восемь специально составленных строк на двух языках. Шесть групп подобраны для покрытия всех выборок, в двух группах по два документа. Это проверка интерфейса, доли на ней не оценивают состав Википедии. Токены в языковой статистике считаются по тексту документа один раз, до BOS/EOS и overlap. В отчёте отдельно приведено число фактически сохранённых ID. Всего 4 русских документа из 8 (50%), 31 текстовый токен из 55 (56,36%), английских — 4 из 8 (50%) и 24 из 55 (43,64%). Таблица показывает число документов и токенов RU / EN и долю русских токенов внутри каждой выборки.

### Предлагаемый отбор пар для полного корпуса

Точные совпадения выделять по хешу, известные связи по work_id и источнику добавлять напрямую. Для близких копий построить дисковый инвертированный индекс уникальных пятисловных шинглов с частотами по документам. Для каждого меньшего множества из n шинглов обходить их в едином порядке от редких к частым (равные частоты упорядочить лексикографически). Порог числа общих шинглов для любой допустимой пары не ниже m = max(20, ceil(0,85 × n)). При n < 20 пару пропускает правило C04.1. Иначе запрашивать списки документов для первых n−m+1 шинглов: если пара имеет хотя бы m общих, хотя бы один находится в этом префиксе. Оставлять кандидатов с размером множества не меньше n, при равенстве размеров обрабатывать пару один раз по ID. Удалять повторные пары, затем считать точные Жаккар и покрытие меньшего документа по исходным порогам. Такой отбор сохраняет пары «отрывок — полная статья» при большой разнице длин. Индекс разбивать по шинглу, пары объединять внешней сортировкой. Для часто повторяющихся фрагментов списки могут быть длинными: обрабатывать их порциями, измерять число кандидатов и сверять полноту с полным перебором на малой подвыборке перед масштабированием.
