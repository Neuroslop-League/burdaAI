# C01. Спецификация модели burdaAI

Версия спецификации — 1. Статус — принята. Документ задаёт нормативное поведение декодера для C03, требования к метаданным токенизатора для C02 и интерфейс логитов для C05 и C06.

## Конфигурация

| Поле | Значение | Назначение |
| --- | ---: | --- |
| `architecture_version` | 1 | Версия настоящей спецификации |
| `num_layers` | 20 | Число блоков декодера |
| `hidden_size` | 2048 | Ширина скрытого представления |
| `num_attention_heads` | 16 | Число голов запросов |
| `num_key_value_heads` | 4 | Число голов ключей и значений |
| `intermediate_size` | 5632 | Ширина каждой входной проекции SwiGLU |
| `max_sequence_length` | 4096 | Максимальная длина входа, включая специальные токены и дополнение |
| `rope_theta` | 10000 | База частот RoPE |
| `rms_norm_eps` | 1e-5 | Добавка к среднему квадрату перед извлечением корня |
| `initializer_std` | 0.02 | Стандартное отклонение начального распределения весов |
| `vocab_size` | из C02 | Число идентификаторов в словаре |
| `tokenizer_id` | из C02 | Неизменяемый идентификатор версии артефакта токенизатора |

Фиксированные значения в таблице обязательны для модели версии 1. При загрузке отклоняются неизвестная версия, несовместимые размеры и отсутствующие обязательные поля. Размер головы вычисляется как `hidden_size / num_attention_heads = 128`, размер группы как `num_attention_heads / num_key_value_heads = 4`. Оба отношения должны быть целыми, размер головы — чётным.

## C01.1. Вычисления декодера

Первая версия использует dense decoder-only Transformer с последовательными residual-блоками, pre-RMSNorm, RoPE и SwiGLU. RoPE задаёт позиции поворотом Q и K без обучаемой таблицы позиций. Pre-RMSNorm сохраняет прямой путь по остаточным соединениям. SwiGLU добавляет вентиль и третью матрицу FFN. Линейные проекции без bias, dropout отсутствует. Источники определений: [RoFormer](https://arxiv.org/abs/2104.09864), [RMSNorm](https://arxiv.org/abs/1910.07467), [GLU Variants Improve Transformer](https://arxiv.org/abs/2002.05202) и [GQA](https://arxiv.org/abs/2305.13245).

### Прямой проход

Для пакета размера B и ширины T embedding возвращает `x` формы `[B, T, 2048]`. Каждый блок последовательно вычисляет:

```text
u = x + attention(rms_attn(x))
x = u + ffn(rms_ffn(u))
```

У `rms_attn` и `rms_ffn` независимые обучаемые векторы масштаба. После 20 блоков применяются отдельная финальная RMSNorm и проекция в пространство словаря. Нормализация обрабатывает последний размер каждого токена:

```text
rms(z, g) = g * z / sqrt(mean(z²) + 1e-5)
```

### Causal GQA и RoPE

Матрицы ниже указаны в порядке `[out_features, in_features]`. Головной формат в формулах — `[B, T, heads, head_dim]`.

| Проекция | Матрица | Выход до объединения голов |
| --- | --- | --- |
| Q | `[2048, 2048]` | `[B, T, 16, 128]` |
| K | `[512, 2048]` | `[B, T, 4, 128]` |
| V | `[512, 2048]` | `[B, T, 4, 128]` |
| O | `[2048, 2048]` | `[B, T, 2048]` после объединения голов |

Для позиции `p`, начиная с нуля, повернуть соседние пары компонент `(2i, 2i+1)` в каждой голове Q и K. Для `i = 0..63` угол равен `a = p / 10000^(2i/128)`. Пары преобразуются как `(x cos(a) − y sin(a), x sin(a) + y cos(a))`. V сохраняется без поворота. Масштабирование позиций отсутствует.

Для головы запроса `h = 0..15` использовать KV-голову `floor(h / 4)`. Для разрешённых ключей `j` оценка внимания равна `dot(Q[p,h], K[j,floor(h/4)]) / sqrt(128)`. Softmax вычисляется по разрешённым ключам одной строки. Результат головы — взвешенная сумма соответствующих V. Выходы голов объединяются в порядке `0..15`, затем применяется проекция O. Реализация может использовать fused GQA при сохранении семантики маски и согласованного численного допуска.

### SwiGLU, инициализация и точность

FFN вычисляет `down(silu(gate(z)) * up(z))`, где `silu(a) = a * sigmoid(a)`. Матрицы gate и up имеют форму `[5632, 2048]`, матрица down — `[2048, 5632]`.

При создании новых весов коэффициенты embedding и всех линейных проекций независимо выбираются из `N(0, 0.02²)`. Общая матрица embedding и выхода инициализируется один раз. Векторы RMSNorm инициализируются единицами. Для воспроизводимости запуск фиксирует seed и окружение. При загрузке сохранённых весов используются их значения.

В BF16 Mixed Precision вычисления RMSNorm, углов и тригонометрии RoPE, а также нормализация softmax внимания выполняются в FP32. В реализации, материализующей оценки внимания, перед масштабированием и softmax оценки приводятся к FP32. Результаты RMSNorm и поворота Q/K приводятся обратно к вычислительному типу слоя. C05 фиксирует точность функции потерь и остальные правила обучения, включая утверждённое хранение состояний оптимизатора в FP32.

## C01.2. Входы, маски и выходы

| Поле | Тип и форма | Семантика |
| --- | --- | --- |
| `input_ids` | int32 или int64, `[B, T]` | Идентификаторы токенов в диапазоне `[0, vocab_size)` |
| `attention_mask` | bool, `[B, T]`, необязательно | `true` обозначает токен, `false` — правое дополнение. По умолчанию все позиции действительны |
| `logits` | вычислительный вещественный тип, `[B, T, vocab_size]` | Ненормированные оценки следующего токена. Позиции правого дополнения содержат нули |

- Требуется `B ≥ 1` и `1 ≤ T ≤ 4096`. Каждая строка содержит хотя бы один действительный токен. Допустимы только непрерывный действительный префикс и правое дополнение.
- Действительный запрос на позиции `p` видит ключ `j`, если `j ≤ p` и `attention_mask[b,j] = true`. Позиции задаются индексом столбца. Для запросов дополнения строку внимания можно пропустить или вычислить с безопасной маской, затем занулить выход слоя внимания. Реализация должна избегать softmax по полностью замаскированной строке.
- Пустые входы, длина больше 4096, неверные формы, типы, идентификаторы и маски отклоняются с ошибкой валидации. Усечение и добавление специальных токенов выполняет вызывающая сторона по правилам C02. Даже идентификаторы заполнителей должны лежать в диапазоне словаря.
- Вызов принимает независимые строки пакета. Дополнительной маски изоляции документов внутри строки в версии 1 нет. C04 формирует строки без упаковки независимых документов, которым нужна изоляция внимания.
- Выход позиции `t` соответствует цели `input_ids[b,t+1]`, если обе позиции действительны и переход разрешён по правилам C04. Последняя действительная позиция пригодна для генерации следующего токена. Сдвиг целей и маску функции потерь применяет C05 по формату C04.
- KV-кэш отложен. Для первой версии C06 при пошаговой генерации передаёт полный текущий префикс и использует логиты последней действительной позиции. Вызывающая сторона останавливается перед шагом, для которого длина входного префикса превысила бы 4096.

## C01.3. Контракт словаря и весов

- C02 передаёт манифест с `tokenizer_id` (непустая строка, однозначно идентифицирующая неизменяемую версию), `vocab_size` (положительное целое) и `special_tokens` (отображение имён ролей в целочисленные ID). Каждый специальный ID входит в диапазон словаря. Допускается общий ID для нескольких ролей, если C02 документирует его семантику. Идентификаторы образуют непрерывный диапазон `0..vocab_size−1` и однозначно задают индекс строки embedding и столбца логитов. Полный список ролей, конкретные ID и алгоритм кодирования определяет C02.
- Embedding и выходная проекция используют одну обучаемую матрицу E формы `[vocab_size, 2048]`. Embedding выбирает строки E, а выход вычисляется как `rms_final(x) @ Eᵀ`. Градиенты обоих применений суммируются в одном параметре.
- C03 сверяет форму E с `vocab_size` при загрузке весов. C05 перед запуском сверяет версию токенизатора и размер словаря в манифесте данных с конфигурацией. C06 выполняет такую же сверку для артефакта токенизатора до генерации. Совпадения размера словаря при несовпадении `tokenizer_id` недостаточно.
- Без отдельного bias и при общих весах число обучаемых параметров равно `901859328 + 2048 × vocab_size`. Точное число станет известно после определения словаря.

## Проверки для передачи в C03 и C05

| Проверка | Ожидаемый результат |
| --- | --- |
| Формы и число параметров | Формы Q/K/V/O и FFN совпадают с таблицей. Подсчёт уникальных обучаемых параметров совпадает с формулой. E учитывается один раз |
| Малый эталон GQA и RoPE | Позиция 0 оставляет пары без изменений. Разные KV-головы дают различимые эталонные значения. Для каждой группы совпадают результаты ручного вычисления и реализации в согласованном допуске |
| Причинность и дополнение | Изменение будущих токенов сохраняет логиты общего префикса в допуске. Короткая строка отдельно и в пакете с правым дополнением даёт те же логиты действительных позиций в допуске. Логиты дополнения равны нулю |
| Границы и валидация | При T = 1 и T = 4096 получаются конечные логиты требуемой формы. T = 0, T = 4097, полностью ложная маска, левое и внутреннее дополнение, ID −1 и ID = vocab_size отклоняются |
| Интеграция с токенизатором | Принимается согласованный манифест. Подмена размера или версии токенизатора обнаруживается до запуска потребителя |
| Граница обучения | На маленьком примере C05 подтверждает соответствие логита позиции t цели t+1 и исключение дополнения из функции потерь |

## Приёмка спецификации

Принята техническим менеджером по результатам проверки размеров, формулы числа параметров и интерфейсов C03 и C05 на контрольных примерах. Значения токенизатора в примере условные.

- **C03.** При `vocab_size = 8` матрица E имеет форму `[8, 2048]`. Для входа `[[3, 5, 0], [4, 6, 7]]` и маски `[[true, true, false], [true, true, true]]` выход имеет форму `[2, 3, 8]`. В первой строке запрос 0 видит ключ 0, запрос 1 видит ключи 0 и 1, логиты третьей позиции равны нулю.
- **C05.** Для того же входа при разрешённых переходах цели составляют `[5, 6, 7]` для логитов в координатах `(0, 0)`, `(1, 0)`, `(1, 1)`. Переход к заполнителю исключается по маске. Конфигурация с идентификатором токенизатора `fixture-a` и размером словаря 8 принимает манифест с той же парой значений. Манифесты с `fixture-b` или размером 9 отклоняются.
- **C02.** Согласован формат передачи метаданных. Выбор токенизатора и реальные значения заполняются в C02.1 и C02.2. C03 может реализовать и проверить интерфейс на условном словаре. Для работы C05 с реальными данными нужен опубликованный артефакт C02.

Проверки реализации из таблицы выполняются в C03 и C05. Проверку спецификации технический менеджер провёл по интерфейсам потребителей. Отдельные подтверждения от разработчиков не получены, поскольку исполнители ещё не назначены.
